# Direct Concierge Inquiry Pipeline Design

## Goal

Replace the customer contact page's `mailto:` workflow with persistent concierge inquiries that staff can manage in the admin dashboard. The feature accepts a small public form, stores each inquiry in the DestinationService database, and gives administrators direct WhatsApp, phone, status, and deletion actions.

## Ownership and persistence

`Tripora.DestinationService` owns the inquiry resource. It already hosts operational admin data and is exposed through the API gateway's destination cluster.

Add an `Inquiry` entity in `Tripora.DestinationService.Models`, mapped to the lowercase `inquiries` table:

| Field | Type | Rules |
| --- | --- | --- |
| `Id` | `int` | Primary key, generated by MySQL auto-increment. |
| `Name` | `string` | Required, maximum 150 characters. |
| `PhoneNumber` | `string` | Required, maximum 50 characters. |
| `Reason` | `string` | Required, maximum 100 characters. |
| `Message` | `string` | Required text. |
| `Status` | `string` | Required; defaults to `UNREAD`; only `UNREAD` or `RESOLVED` are valid. |
| `CreatedAt` | `DateTime` | UTC creation time; database default timestamp. |

`DestinationDbContext` exposes `DbSet<Inquiry> Inquiries`. Fluent configuration uses the table/column names above and indexes `(Status, CreatedAt)` so the unread desk remains fast. An EF Core migration creates the table; there is no seed data.

## HTTP contract

All endpoints are rooted at `/api/inquiries`. The API gateway receives both a base route and a catch-all route forwarding to the DestinationService cluster.

| Method and route | Access | Request | Response |
| --- | --- | --- | --- |
| `POST /api/inquiries` | Anonymous | `{ name, phoneNumber, reason, message }` | `201 Created` with the created inquiry. |
| `GET /api/inquiries` | Admin JWT role | None | Inquiry array, newest first. |
| `PATCH /api/inquiries/{id}/status` | Admin JWT role | `{ status: "UNREAD" | "RESOLVED" }` | Updated inquiry. |
| `DELETE /api/inquiries/{id}` | Admin JWT role | None | `204 No Content`. |

The controller returns `400 Bad Request` for invalid payloads/statuses and `404 Not Found` for missing IDs. It keeps public submission anonymous but protects listing and all staff actions with `[Authorize(Roles = "Admin")]`.

DestinationService's existing CORS policy already accepts all headers and methods for configured frontend origins; no controller-level CORS rule is added.

## Customer contact experience

`Contact.jsx` uses the shared API client and reduces the form to Name, Phone Number, Reason, and Message. Email, destination, travel month, and guest fields are removed along with all `mailto:` construction.

Submitting disables the action while `POST /inquiries` is in flight. Success clears the form and shows a clear on-page confirmation. Validation or server errors remain on the page without clearing entered values. Existing direct hub telephone and WhatsApp links remain available.

## Admin concierge desk

The dashboard's `inquiries` navigation item renders a dedicated `InquiriesModule`, not a generic CRUD form. On entry it requests `/inquiries` and displays a crystalline ledger with:

- guest name, phone number, reason, message, and created timestamp;
- a status control that changes `UNREAD` and `RESOLVED` through the PATCH endpoint;
- a telephone link using the normalized phone number and a WhatsApp link using `https://wa.me/<digits>`;
- a delete action with confirmation;
- loading, error, and empty states.

The overview request also fetches inquiries and calculates `openInquiriesCount` from `UNREAD` records. Mutating a desk row updates its local state and refreshes the overview on the next dashboard refresh.

## Error handling and safety

The public form exposes only non-sensitive contact details requested by the user. Server-side data annotations and controller checks are authoritative. Admin mutations rely on JWT role authorization; the UI does not imply authorization by itself. WhatsApp/phone actions are regular external links and do not transmit a message until staff chooses to do so.

## Verification

- DestinationService compiles with the migration and controller.
- Frontend tests cover contact payload submission, success/error state, inquiry listing, status toggling, direct-contact links, and deletion confirmation.
- Dashboard live-data coverage asserts the overview unread count.
- A frontend production build validates the application bundle.
